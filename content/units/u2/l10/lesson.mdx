# Review mastery: AGENTS.md rules, deny.toml, planted-bad-diff hunting

Getting PRs merged is half writing code and half reviewing it. Goose's
review doctrine is written down in exactly the places reviewers grep: the
`Rules` section of AGENTS.md (`AGENTS.md:91`) and the `Never` section
(`AGENTS.md:111`). Learn to review against those two lists and you will also
stop *writing* violations.

## The review checklist, from the files that define it

**Behavior rules (`AGENTS.md:91-99`)** — every PR must respect: tests in
`tests/` (`:93`), self-test recipe updated (`:94`), errors as
`anyhow::Result`, providers via the `Provider` trait, MCP glue in
`goose-mcp`, plus the parity rule you internalized in l06.

**Never rules (`AGENTS.md:111-119`)** — instant review comments: skipping
`cargo fmt`; merging without clippy; comments that restate code; hand-editing
`Cargo.toml` dependency entries instead of `cargo add` (with `Cargo.lock`
kept consistent); overwriting live binaries in place.

## Dependency policy = security posture

`deny.toml` sits at the repo **root** (legacy plan documents said
`rust-toolchain/deny.toml` — the file moved; root is the truth now). The
policy (`deny.toml:1-9`): `yanked = "deny"` — any yanked crate bricks CI,
emulating cargo-audit's supply-chain check, with `unmaintained`/`unsound`
deliberately at `none`. Exceptions exist only in the `ignore` list, and each
carries a *why* comment (`:9` — a justified RUSTSEC ignore). The policy runs
in `.github/workflows/cargo-deny.yml`. Reviewing a dependency PR therefore
means: was it added via `cargo add`? is the lockfile consistent? does any new
crate trip `yanked`?

```toml
# deny.toml — exception with the mandatory reason comment (illustrative id)
[advisories]
yanked = "deny"

ignore = [
    "RUSTSEC-0000-0000",  # why: no safe upgrade available yet — re-check each release
]
```

An `ignore` entry without that comment is itself a review finding: the whole
point of the list is that exceptions stay *accounted*. One release later the
reason may be stale, and the reviewer re-tests it.

<FounderLens>

Why deny yanked crates so hard? A yanked version is the crate author shouting
"this is broken, don't use it" — publishing a security incident in metadata.
Tradeoff: strictness costs the occasional forced dependency bump mid-release.
The design answer is the `ignore` list with mandatory reasons: exceptions are
allowed, documented, and reviewable — not silent. Where it breaks: reviewers
who copy an existing `ignore =` entry without verifying its reason stays
valid (the RUSTSEC comment says *no safe upgrade available yet* — that ages).

</FounderLens>

## Hunting planted violations — the reviewer's instinct

When a diff looks clean, interrogate it anyway:

1. Does every changed behavior appear in *both* agent-loop universes?
2. Is every lint silence (`#[allow]`, `#![allow]`) explained?
3. Does every new error path use `anyhow`/`?` — no fresh `unwrap()`?
4. Do new deps arrive via `cargo add` with a consistent lock?
5. Are tests in the preferred folder, and do they prove the claim?

The repo ships its own recipe for this (`code-review.yaml`) — review is a

to catch.
