# Match and pattern matching: the compiler checks your cases

TS `switch` falls through, forgets cases, and needs `break;`. Rust `match` is a
*type-checked exhaustiveness proof*. Delete a case and the compiler tells you
exactly which variant you forgot. That changes how goose is written.

## Read a real enum first

`crates/goose/src/agents/retry.rs:23`:

```rust
pub enum RetryResult {
    Skipped,                                // no data
    MaxAttemptsReached(Message),            // carries a Message
    SuccessChecksPassed,
    Retried,
}
```

Match it:

```rust
match retry_result {
    RetryResult::Skipped => { /* nothing */ }
    RetryResult::MaxAttemptsReached(msg) => {
        println!("failed: {}", msg.debug());
    }
    RetryResult::SuccessChecksPassed => { /* celebrate */ }
    RetryResult::Retried => { /* loop again */ }
}
```

Every arm names a variant; a variant with a payload *must* bind it (`msg`).
Remove one arm → compile error, not a silent miss.

## `if let` — when you only care about one shape

`crates/goose/src/token_counter.rs:90`:

```rust
if let Some(serde_json::Value::Object(properties)) =
    tool.input_schema.get("properties")
{
    // only runs when the schema really has a properties object
}
```

Read as: "if this pattern matches, run the block." It's `match` for the one-arm
case — goose's main guard-clause tool. Two siblings worth knowing at the same
price:

```rust
// matches! — the pattern as a yes/no expression
let retrying = matches!(result, RetryResult::Retried | RetryResult::Skipped);

// while let — "keep going while the pattern holds" (e.g. draining a queue)
while let Some(block) = queue.pop_front() {
    render(block);
}
```

## Refutability and destructuring

Patterns *destructure* real goose data. `testprovider.rs:91` cleans a message
out of internal metadata before hashing:

```rust
match content {
    MessageContent::ToolRequest(ref mut req) => {
        req.tool_meta = None;
    }
    MessageContent::ToolResponse(ToolResponse {
        tool_result: Ok(ref mut result @ CallToolResult { is_error: Some(false), .. }),
        ..
    }) => {
        result.is_error = None;
        result.result_type = None;
    }
    _ => {}
}
```

`ref mut` borrows the inner value mutably; `@` binds a name to the *whole* inner
pattern; `..` means "ignore the rest of the fields". The trailing `_ => {}` is
the explicit "everything else" arm.

Match reads as a decision table — each arm a separate, compiler-witnessed
route:

## A quick exhaustiveness exercise (preview: goose's compiler is your teacher)

Note `SuccessCheck` at `crates/goose/src/agents/types.rs:61` has exactly one
variant today. That's a bet by the goose team: they'd rather add variants later
(with the compiler pointing at every match site to update) than over-model now.

<FounderLens>

Why does goose clean message content before hashing in `testprovider.rs:91`?
Inputs must hash identically against recorded responses — internal routing
metadata (tool ownership, is_error flags) that varies run-to-run must not leak
into the key. Pattern matching lets the cleanup read like a spec: each branch
names exactly the field being neutralized. Tradeoff: adding a new
`MessageContent` variant forces updates in every `match` — the compiler walks
you to each one. Where it breaks: `..` and `_` arms can hide the need to update
logic when the intent was "all cases".

</FounderLens>

<MindShift>

TS `switch` is a statement you can forget. Rust `match` is a proof you must
complete. When reading goose and you want to change an enum's variants, expect
the compiler to hand you a list of every match site in the codebase — that list
is literally your task queue. Code review in Rust starts from exhaustiveness,
not from guessing.

</MindShift>
