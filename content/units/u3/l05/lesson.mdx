# Registration & auth: registry, provider_secrets, OAuth

A `Provider` impl is inert until something can *construct* it, and worthless
to a user until its credentials are *stored safely*. This lesson closes the
loop: registry, secrets, OAuth.

## The registry

`crates/goose/src/providers/provider_registry.rs` is the single map from
provider name to `ProviderEntry` (line 26) — metadata, a lazy constructor
(`ProviderConstructor`, line 12), and inventory resolvers. Registration happens
at startup; the registry holds **no instances**, only "how to build one."
The constructor receives `Vec<ExtensionConfig>` (the config.yaml extensions)
plus TLS config, and returns `Arc<dyn Provider>`.

The constructible contract is `ProviderDef`
(`crates/goose/src/providers/base.rs:31`): `ProviderDescriptor::metadata()`
declares `config_keys` — named settings each flagged `secret` or not — and
`from_env(...)` actually builds the instance, reading secrets from the
environment. Providers that hold long-lived sessions add cleanup hooks and
inventory resolvers ("which models does this account have?").

## provider_secrets: the credential ledger

`crates/goose/src/providers/provider_secrets.rs` models every credential goose
manages as a `ProviderSecret` (line 32): `storage` distinguishes the OS
secret store (`secret_store:`-prefixed ids, line 13) from a simpler cache;
`status` is Valid/Expired/Unknown (derived from `expires_at`); `configured` and
`has_secret` separate "user configured it" from "secret value actually stored".
Providers whose tokens expire (OAuth refresh tokens) mark `can_configure: true`
and point `configure_provider` at the flow that renews them — the two fields
together ("renewable?" + "via which flow") drive the UI's reauth affordance.

## OAuth flows

`crates/goose/src/providers/oauth.rs` implements provider OAuth the hard way:
it spins an **axum loopback server** for the redirect, enforces
`endpoint_transport` (line 25) — HTTPS mandatory for remote auth endpoints,
plain HTTP allowed **only on loopback** — and serializes all flows behind one
`OAUTH_MUTEX` (line 17) so two simultaneous logins cannot step on each other.
Device-flow variants live alongside (`oauth_device_flow.rs`). On the *extension*
side, `streamable_http` MCP servers that return `AuthRequired` are handled by
`create_streamable_http_client`
(`crates/goose/src/agents/extension_manager.rs:1105`) completing the OAuth
handshake before the first tool call.

<FounderLens>

Why a registry *and* a trait? Providers must be constructible before config
exists (for the `goose provider configure` surface), lazily (the user may never
load nine of ten providers), and rebuildable (config edits must not restart the
process). That rules out a static `Vec<Arc<dyn Provider>>`. The registry's
sharpest edge is the constructor signature: `Vec<ExtensionConfig>` means every
provider construction is *runtime-config dependent* — an unrecognized field
anywhere can poison construction for an unrelated provider, subtly. The secrets
design splits storage from metadata for the same reason the registry splits
construction from instance: the UI needs to display "configured but not secret"
without ever touching secret material.

</FounderLens>
