# Plugins & skills: slash commands and the skills/ directory

Providers and MCP servers are *capability* extensions. Plugins are *packages*:
a git repo bundling commands, skills, hooks, and MCP configs, installed with one
command. This lesson builds an installable plugin whose skills light up as
slash commands in goose.

## What makes a repo a plugin

A repo is an Open-Plugins-format plugin if it has any `COMPONENT_MARKERS`
(`crates/goose/src/plugins/formats/open_plugins.rs:21`):

- `hooks/hooks.json` — lifecycle hooks (l09's subject)
- `commands/` — markdown prompt files. This is an Open-Plugins install marker:
  in goose v1.49.0 no runtime consumer turns `commands/*.md` into anything yet
  (builtins, recipes, and *skills* are what light up as slash commands) —
  other Open-Plugins hosts read them
- `agents/` — bundled sub-agent definitions
- `.mcp.json` — bundled MCP servers

plus the optional `plugin.json` manifest for `name`/`version`/`skills`/
`mcpServers`. Installation (`goose plugin install <url>` —
`crates/goose-cli/src/cli.rs:706`) checks out the repo into a staging dir,
validates names + MCP docs, rewrites skill names to namespaced form, writes
`.goose-plugin-install.json` metadata (`crates/goose/src/plugins/mod.rs:17`),
and atomically renames into place. Auto-update checks run every 24h.

## Skills become slash commands

A skill is a `SKILL.md` with frontmatter — `SkillFrontmatter`
(`crates/goose/src/skills/mod.rs:33`) where `name` and `description` are the
significant fields (both `serde(default)` — when absent, name is inferred from
the skill's directory and description is empty); everything else goes into a
free-form `metadata` bag per the agentskills.io spec. `discover_enabled_plugins`
(`crates/goose/src/plugins/discovery.rs:52`) walks user
(`~/.agents/plugins`) and project (`.agents/plugins`) roots; plugin
skills are surfaced **namespaced** (`plugin-name:skill-name`) so two plugins
can each ship a `deploy` skill without collision. `skill_slash_command.rs:8`
turns every discovered skill into a slash command listing; merge order is
builtins, then recipes, then skills — later sources never shadow reserved or
earlier names (`slash_command.rs:11`).

Skills also carry a content-body semantics you already know from MCP servers:
the SKILL.md body is *instructions*, spliced into context when invoked — it is
a prompt library, not a script.

<FounderLens>

The plugin design's centerpiece is that **a plugin is files, not code**:
markdown, JSON, YAML. That is why install can be atomic-staged, namespaced,
and auto-updatable — nothing compiles. The tradeoff is expressiveness parity:
`commands/` prompts and skills can't run code, so anything stateful must move
into `hooks/` scripts or `.mcp.json` servers. The collision rule (builtins
reserved, first writer wins) falls out of the fear that a plugin could shadow
a core command — a shadowing `deploy` would be indistinguishable from the
builtin in the UI. Namespacing is how the system stays open *and* safe.

</FounderLens>
