# Advanced: hooks, permission rules, subagents

Three mechanisms push extensions from "capable" to "production-safe":
lifecycle hooks (react without being asked), permission rules (ask instead of
assume), and subagents (delegate whole projects of work).

## Hooks: subscribe to the agent's life

A plugin's `hooks/hooks.json` subscribes to events from a fixed alphabet —
`HookEvent` (`crates/goose/src/hooks/mod.rs:55`): `PreToolUse`,
`PostToolUse`, `PostToolUseFailure`, `SessionStart/End`,
`UserPromptSubmit`, file/shell before-after pairs, `Stop`. Each entry pairs a
`matcher` (tool-name regex like `developer__shell|developer__text_editor`)
with actions; goose currently supports `{"type":"command"}` actions. The
command receives the JSON event payload on **stdin** and answers via stdout —
and there are two answer grammars:

- **non-blocking** events: exit 0. Optional stdout JSON `{"banner": …}`
  surfaces text in the UI.
- **blocking** events (`PreToolUse` and friends, `emit_blocking` at line 703):
  stdout must be `{"decision":"block","reason":"…"}` or
  `{"decision":"allow"}`; kind of negative-claim — empty stdout with exit 0
  means *allow*. A hook can also deny by exiting with status code 2 and the
  reason on stderr (documented at `hooks/mod.rs:700-702`). Failures fail
  **open** unless the hook sets `"on_failure": "block"`. A hook that hangs
  dies alone at `DEFAULT_HOOK_TIMEOUT_SECS` (line 44).

## Permission rules: rememberable decisions

The permission system is typed around shared `Permission` /
`PermissionConfirmation` (`crates/goose/src/permission/mod.rs:5`).
`ToolPermissionRecord` (`permission_store.rs:12`) stores each approval:
tool name, `allowed`, a hash of the call's **context** (`context_hash`, so
"allow rm on this exact dir" is scoped), plus `expiry`. "Always allow for this
session" desugars to a record without expiry; the store is what makes goose
*remember*. Separately, the judge (`permission_judge.rs:41`) classifies
incoming requests read-only vs write by asking the model itself with a
structured scoring tool.

## Subagents: delegate, don't broadcast

A subagent is a *nested agent run*: `run_subagent_task`
(`crates/goose/src/agents/subagent_handler.rs:47`) takes `SubagentRunParams`
(line 36) — config, recipe, `TaskConfig`, `return_last_only`, session id,
cancellation token, notification channel — and returns a string result to the
parent loop. The turn budget lives on the `TaskConfig` itself
(`max_turns: Option<usize>` at `subagent_task_config.rs:19`). Plugins can
bundle `agents/` definitions (an Open-Plugins component marker); the parent
agent only sees the final output, keeping its own context small.

<FounderLens>

The unifying idea: *control surfaces that respect the agent's shape*.
Hooks get a restricted event alphabet instead of arbitrary code injection;
blocking hooks must speak two-verb JSON instead of exit-code folklore;
permissions hash the *context* so the "remember" promise can't be blanketed
indefinitely by default; subagents parallel the OS notion of a worker
process — bounded, observable, disposable. The tradeoff everywhere is
expressiveness: a hook cannot prompt the user, a permission record cannot
fine-grain `prewrite` the tool's internal state, and a subagent's context is
invisible to the parent. Extensions live with those walls; that is what keeps
the agent's context budget, safety, and debuggability intact.

</FounderLens>

## The lab

Put all three to work in your plugin: a real blocking hook chain, a
permission rule sketch with remember-scoping, and an `agents/` definition
wired the way `run_subagent_task` expects.
