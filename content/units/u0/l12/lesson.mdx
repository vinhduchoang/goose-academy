# Generics and traits: a preview of how Provider works

Traits are TS interfaces that *implementations must sign up for*; generics are
where you'd write `T extends Base` in TS. Goose is trait-obsessed — and the one
trait that runs the whole product is `Provider`.

## Read the real abstraction

`crates/goose-provider-types/src/base.rs:464`:

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    async fn stream(
        &self,
        model_config: &ModelConfig,
        system: &str,
        messages: &[Message],
        tools: &[Tool],
    ) -> Result<MessageStream, ProviderError>;
    // ... complete(), get_context_limit(), etc. with defaults
}
```

`Provider: Send + Sync` is a *supertrait bound*: implementors must be safe to
send across threads — non-negotiable for an agent that hugs HTTP pools. Goose
uses the `#[async_trait]` macro because it works with trait objects: native
async fns in traits make the trait non-dyn-compatible, and goose runs providers
as `Arc<dyn Provider>` throughout (`providers/init.rs`).

## Trait objects: `Box<dyn Provider>`

`MessageStream` at `base.rs:327`:

```rust
pub type MessageStream = Pin<
    Box<dyn Stream<Item = Result<(Option<Message>, Option<ProviderUsage>), ProviderError>> + Send>,
>;
```

`Box<dyn Stream>` = "some heap-allocated value implementing `Stream`" — exactly
your TS `Promise<Iterator<T>>` mental model, except the item type is checked.
And you already met `Arc<dyn Provider>` — the same dyn idea, shared
(`crates/goose/src/agents/types.rs:7`).

## Generics in your own code

```rust
fn summarize<T: Display>(items: &[T], max: usize) -> String {
    items.iter().take(max).map(|i| i.to_string()).collect::<Vec<_>>().join(", ")
}
```

`T: Display` — "any type with a Display impl". Goose's equivalent from
`model.rs:103`:

```rust
pub fn new(model_name: impl AsRef<str>) -> Self {
```

`impl AsRef<str>` is sugar for a generic param — reads "anything string-like".

One function, any Display type — the compiler stamps out a version per call
(static dispatch):

```rust
let fmt_nums = summarize(&[1u64, 2, 3], 2);          // "1, 2"
let fmt_names = summarize(&["goose", "agent"], 5);   // "goose, agent"
```

`u64` and `&str` share no base type — they only share the `Display`
contract. That is the whole trick: code is written against behaviors
(traits), not shapes (inheritance trees).

## Where Provider generics appear in practice

Look how goose *consumes* providers without knowing which one it holds:
`ProviderDef` (a descriptor for registry discovery) wraps
`type Provider = Self;` associated type at `testprovider.rs:156` — the generics
machinery you'll fully dissect in Unit 1 (provider registries) and Unit 3
(building your own provider).

<FounderLens>

Why `Complete` with a default implementation instead of two required methods
(`base.rs:485+`)? Most providers implement `stream`; `complete` = "collect the
stream" (`collect_stream`) is boilerplate — a default impl means a new provider
ships by writing ONE function. Tradeoff: default methods can hide cost
(collecting a stream buffers everything) — providers that care override. Where
it breaks: `MessageStream` being boxed hides which concrete stream it is —
debugging cross-provider stream behaviors takes type-erasure skills. That's
exactly the "where would streaming break" question Unit 1 asks.

</FounderLens>

<MindShift>

TS interfaces are structural: anything with matching shape fits, silently.
Rust traits are nominal: a type is a Provider only if it *declares*
`impl Provider`. Structural typing is why TS can't tell "accidental interface
match" from "real contract." In goose, `impl Provider for X` is a recorded,
searchable commitment — grep `impl Provider for` and you have the full list of
every LLM backend goose has ever shipped.

</MindShift>
