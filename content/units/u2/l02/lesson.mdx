# Bug reproduction & bisecting: from issue to culprit commit

Goose PRs are graded on verification plans, and the cheapest verification of a
bug fix is a **reproduction**: the exact inputs that turn good code into bad
output. The bug template asks for numbered repro steps (`bug_report.md:21`)
before anything else, and for the diagnostics zip (`bug_report.md:14`) so the
maintainer spends zero time on your environment.

## Reproduction is a contract

A repro has three parts, all falsifiable:

1. **Given** — version (use `git describe --tags`), OS, minimal config.
2. **When** — the exact commands/inputs, numbered.
3. **Then** — observed output vs expected output.

If you cannot reproduce an issue from its report, the report is under-triaged
— write the missing repro step as a comment before touching code. Every goose
regression test you will write later is just a repro statement turned into an
assertion.

A real example from this repo's own history: issue #4632 — `token_counter`
panicked when used with GitHub Copilot. The fix (`509fcac69`) is instructive
because it is tiny: +3/-1 in one file. A panic is usually a one-line root
cause hiding inside a complex call chain; repro turns the search for that line
into a search with a trigger.

## Bisect: binary search over history

`git bisect` automates the second half of the hunt: which commit introduced
the regression. The mechanics:

```text
git bisect start
git bisect bad            # current commit shows the bug
git bisect good <older-sha>   # a commit where the bug did not exist (this clone has no release tags)
# git checks out the midpoint; run your repro on it:
#   repro fails -> git bisect bad
#   repro passes -> git bisect good
# repeat until: "X is the first bad commit"
git bisect log            # permanent record
git bisect reset
```

The magic is the midpoint checkout — git jumps to the half-way commit and lets
your repro script be the judge. With one runnable repro you need ~log2(N) runs
instead of N.

## Making the repro a script pays double

A one-command repro (`.\check.ps1` or `cargo test --package goose some_test`)
turns bisect into near-full automation:

```text
git bisect run .\check.ps1
```

`bisect run` replays the repro on each midpoint and reports the first bad
commit without you pressing any keys. Exit 0 = good, non-zero = bad.

<FounderLens>

Why does goose tolerate ~5,600 commits of history instead of squashing? Because
history IS the debugging tool: bisect needs real intermediate states. Tradeoff:
linear readable history vs bisectable history — goose picks bisectable, and
that is why contributors are asked to keep commits small and individually
coherent. Where it breaks: merges create non-linear histories where `first bad
commit` can be misleading — treat the reported commit as a hypothesis, then
confirm by reading its diff.

</FounderLens>
