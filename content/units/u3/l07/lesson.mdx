# MCP II: schemas, errors, elicitation, auth — hardening a server

Lab 3.6's server works on well-behaved input. Production means hardening: schemas
that fail loudly, errors the agent can *recover* from, a way to ask the user
mid-call, and a credential boundary. All four are protocol features goose
already speaks — you set the server side up, goose handles its half.

## Schemas constrain shape — never meaning

`JsonSchema` on params guarantees types, nothing more. `text` can be a
megabyte of spaces; `tag` can be `"__proto__"`. That is why the reference
server guards *inside* the tool
(`crates/goose-mcp/src/memory/mod.rs:402`): semantic checks live in the
handler, and the failure channel is `ErrorData` with a protocol `ErrorCode` —
`INVALID_PARAMS` for caller faults, `INTERNAL_ERROR` for yours. The agent reads
that distinction: it re-phrases on `INVALID_PARAMS`, it tells you to file a bug
on `INTERNAL_ERROR`.

```rust
// harden every handler the same way: shape from the schema, meaning from a guard
if content.chars().count() > 10_000 {
    return Err(ErrorData::new(
        INVALID_PARAMS,                // caller's fault -> model re-phrases
        "note too long: keep it under 10_000 characters",
    ));
}
```

Error text is part of the *protocol* the model reads: say what was rejected
and what a valid value looks like — the model uses that text to recover.

## Errors the agent can act on

Goose's tool pipeline propagates tool errors into the transcript with the
`is_error` flag — a failed `CallToolResult` becomes a message the model sees,
so honesty in error text is a feature, not a courtesy: include what was
rejected, and what a valid value would look like. Reserve timeouts for the
infrastructure layer: spawns die at `DEFAULT_EXTENSION_TIMEOUT` of 300s
(`crates/goose/src/config/extensions.rs:10`), and per-call cancellation is
separate.

## Elicitation: ask a human mid-call

Sometimes the tool cannot proceed without a human decision (pay money, pick a
branch). MCP models this as *elicitation*: the server issues an `Elicit`
request; goose renders the question via its action-required manager and learns
one of three outcomes — `Accept(user_data)`, `Decline`, `Cancel`
(`crates/goose/src/action_required_manager.rs:16`). The response is mapped back
to rmcp's `ElicitationAction` (`crates/goose/src/elicitation.rs:16`) and
delivered as a message; the MCP client carries the `ElicitRequestParams`
request type (`crates/goose/src/agents/mcp_client.rs:11`).

## Auth: two doors

- **stdio servers**: an API key arrives either via `env_keys` (goose feeds the
  configured secret) or per-request meta headers; the tool checks and rejects
  with `INVALID_REQUEST`-class errors.
- **streamable_http servers**: the server answers `AuthRequired`; goose runs the
  pre-registered OAuth client through
  `create_streamable_http_client`
  (`crates/goose/src/agents/extension_manager.rs:1105`) before the first call.

And the config side of MCP: every `.mcp.json`/manifest entry is schema-checked
by `validate_mcp_servers_manifest_value`
(`crates/goose/src/plugins/mcp_servers.rs:171`) long before a process spawns.

<FounderLens>

Why is elicitation a *protocol* feature instead of "just make it another
tool result"? Because a tool call is synchronous in the loop — a
blocks-the-world question needs a first-class channel, and MCP chose
Accept/Decline/Cancel as the minimal human-answer alphabet. Goose's
ElicitationOutcome is that alphabet, verbatim. The hardness tradeoff: every
elicitation consumes a user's attention, so hardened servers must make
elicitation *rare and decidable* — a bad auth token must NOT elicit, it must
fail fast, or malicious servers can turn the user into a dialog box.

</FounderLens>
